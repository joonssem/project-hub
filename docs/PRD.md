# Project Hub PRD

작성일: 2026-10-13 · 상태: 초기 제품 기준 · 버전: 1.1

개발 방향 검토에 따라 정적 구조를 유지한다. 상태·저장소 주소를 추가하고 초기 호스팅은 GitHub Pages로 결정했다. 실제 배포·학생 iPad 검증은 남아 있다. 최신 상태는 [작업 기록](work-log.md), [검토 보고](review-2026-10-13.md), [데이터 계약](data-contract.md)을 따른다.

## 1. 제품 방향

**프로젝트는 독립적으로 개발하고, 정보는 한곳에서 관리하며, 이용자에게는 필요한 것만 보여준다.**

Project Hub는 여러 웹앱과 디지털 자료의 정보를 모아 학생·교사·발표 청중이 필요한 프로젝트를 찾고 실행하도록 돕는 카드형 포털이다. 제품의 우선 가치는 로그인이나 관리 시스템의 규모가 아니라, 실제 자료를 쉽게 찾고 올바른 실행 주소로 이동하는 데 있다.

각 프로젝트의 저장소·배포 주소·게임 코드·DB·로그인은 독립적으로 유지한다. `D:\Projects\mini_game_platform`은 허브의 프로젝트 한 개로 등록한다. 허브 로그인과 게임 로그인 통합은 범위에 포함하지 않는다.

## 2. 해결할 문제

- 제작한 자료가 여러 주소에 흩어져 수업·공유·발표 때 다시 찾기 어렵다.
- 학생과 동료 교사에게 필요한 자료가 달라 같은 목록을 그대로 보여주기 어렵다.
- 발표마다 링크를 다시 모으거나 순서를 정하는 작업이 반복된다.
- 프로젝트 설명과 활용 방법을 기억에 의존하면 재사용하기 어렵다.

초기에는 제작자 한 명이 관리하고 방문자는 로그인 없이 공개 자료를 이용하는 운영을 가정한다. 다중 관리자와 비공개 자료 접근은 필요가 확인된 뒤 확장한다.

## 3. 사용자와 핵심 작업

| 사용자 | 해야 할 일 | 성공한 상태 |
| --- | --- | --- |
| 학생 | 안내받은 게임·수업 자료 찾기 | 학생용 화면에서 알맞은 카드를 찾아 실행 |
| 동료 교사 | 자료의 목적과 활용 방법 파악 | 설명·공개 활용 사례를 읽고 자료 실행 |
| 발표자 | 선정한 프로젝트를 순서대로 소개 | 프리셋 URL을 열어 준비한 순서로 시연 |
| 제작자·관리자 | 목록과 공개 설정을 정리 | 정보를 수정하고 저장·배포 결과 확인 |

관리자는 허브의 목록 편집자다. 개별 프로젝트 내부의 사용자·게임 진행·데이터를 관리하지 않는다.

## 4. 우선순위

P0는 첫 실제 사용 전에 필요한 항목, P1은 핵심 활용을 확인한 뒤 개선할 항목, P2는 도입 조건이 충족될 때만 착수할 항목이다. 이미 구현된 기능도 실제 데이터와 사용 검증을 마치기 전까지 완료로 보지 않는다.

| 우선순위 | 항목 | 이유 | 완료 기준 |
| --- | --- | --- | --- |
| P0 | 실제 프로젝트 목록과 정확한 링크 | 연결할 실제 자료가 있어야 포털 가치가 생김 | 첫 사용에 필요한 자료 등록, 예시 명시 또는 제거, 실행 링크 수동 확인 |
| P0 | 학생·교사 대상별 카드 화면 | 필요한 자료만 찾는 핵심 경험 | 공개 대상과 숨김 규칙을 충족하는 카드만 표시 |
| P0 | 이름·설명·이미지·태그와 실행 동작 | 선택과 실행에 필요한 최소 정보 | 읽기 쉬운 카드, 이미지 대체 표시, 주소 없는 카드의 상태 안내 |
| P0 | 공개 데이터 경계와 검증 | 필터를 접근 제한으로 오해하거나 비공개 정보를 노출하지 않도록 함 | 공개 JSON 검토, 위험한 주소와 잘못된 데이터 거부 |
| P0 | 모바일·키보드 사용과 기본 오류 처리 | 수업 기기와 화면 크기가 다양함 | 주요 작업 수행 가능, 로딩·빈 목록·실패 상태 안내 |
| P0 | 실제 배포와 운영 절차 | 로컬 구현을 실제 사용으로 연결 | 호스팅 선정, 배포 URL 확인, 수정·배포·복구 절차 기록 |
| P1 | 검색·태그 탐색 개선 | 목록이 늘어날 때 찾는 시간을 줄임 | 실제 태그와 검색어로 자료 발견 가능 |
| P1 | 발표·연수 프리셋 | 자료를 반복 선정하는 작업을 줄임 | 선정 목록·순서·설명 저장, 직접 URL로 재사용 |
| P1 | 교사용 공개 활용 사례 | 자료의 수업 활용 판단을 도움 | 실제 사례를 공개 가능한 내용으로 작성 |
| P1 | 로컬 관리자 편집 편의 | JSON 수정을 돕는 보조 기능 | 검증된 데이터 가져오기·편집·내보내기, 저장 방식 안내 |
| P2 | 관리자 인증과 웹 저장 | 파일 교체 방식이 실제 운영에 불편해질 때 필요 | 관리자만 조회·변경 가능한 요청, 영구 저장과 복구 검증 |
| P2 | 다중 관리자와 변경 이력 | 공동 관리가 시작될 때 필요 | 계정별 권한, 변경자·변경 내용 추적 |
| P2 | 피드백·활용 기록 수집 | 현장 개선 요구가 확인될 때 필요 | 수집 목적·동의·보관·삭제 정책을 정한 뒤 구현 |

검색·프리셋·로컬 편집 등 이미 구현된 P1 기능은 유지한다. 이 기능을 추가 고도화하느라 실제 콘텐츠 등록과 P0 검증을 늦추지 않는다.

## 5. 초기 출시 범위

### 학생용

- 기본 진입 화면은 학생용이다.
- `hidden=false`이고 `student=true`인 프로젝트를 표시한다.
- 카드에서 이름·설명·태그·대표 이미지와 실행 상태를 확인한다.
- 실행 링크는 새 탭에서 열며 개별 서비스의 로그인 요구는 해당 서비스가 처리한다.

### 교사용

- `hidden=false`이고 `teacher=true`인 프로젝트를 표시한다.
- 카드 정보와 공개 활용 사례를 제공한다.
- 교사용 화면은 공개 자료를 교사 관점에서 구성한 화면이다. 교사 신분 확인 기능은 초기 범위에 없다.

### 발표·연수용

- 프리셋 이름·설명과 선정 프로젝트를 지정 순서로 표시한다.
- 프리셋은 학생·교사 공개 설정과 별도로 선정한다. 프리셋 선정은 해당 공개 화면에 소개하겠다는 의사로 취급한다.
- 숨김 프로젝트는 프리셋에서도 제외한다.
- 빈 프리셋에는 빈 상태를 표시한다. 없는 프리셋 ID는 기본 프리셋으로 전환하고, 프리셋이 전혀 없으면 등록 안내를 표시한다.
- `view`와 `preset` 쿼리로 화면 주소를 공유한다. 검색·태그 상태의 URL 저장은 초기 필수 범위가 아니다.

### 관리자 편집 도구

- 전체 프로젝트 등록·수정, 숨김과 대상별 표시 설정, 프리셋 편집을 제공한다.
- JSON 파일 직접 수정도 공식 관리 방법으로 지원한다.
- 초기 편집 도구에는 인증·서버 저장이 없다. 편집은 현재 탭의 메모리에만 적용한다.
- JSON 내보내기 후 원본 교체·배포까지 해야 방문자에게 변경이 반영된다. 다운로드 자체를 영구 저장 완료로 안내하지 않는다.
- 공개 페이지로 접근 가능한 편집 도구는 누구나 열 수 있지만 서버 원본을 변경할 수 없다. 비공개 관리자 기능으로 소개하지 않는다.
- 프로젝트 삭제 UI는 초기 필수 범위가 아니다. 우선 숨김으로 관리하며, 파일에서 삭제할 경우 프리셋 참조도 정리하고 검증한다.

## 6. 데이터와 공개 정책

초기 원본은 버전 관리 가능한 `data/projects.json`이다. 데이터 계약의 상세는 [기존 요구사항](requirements.md)을 따른다.

| 정보 | 초기 처리 |
| --- | --- |
| 이름·설명·이미지·실행 주소·태그 | 공개 가능 정보만 저장 |
| 학생·교사 공개 여부·숨김 | 화면 표시를 결정하는 값 |
| 활용 사례 | 작성자가 정리한 공개 설명, 자동 이용 로그와 구분 |
| 프리셋 | 이름·설명·프로젝트 ID와 순서 |
| 비공개 메모·개인정보·비밀키 | 공개 JSON에 저장 금지 |
| 저장소 주소·프로젝트 상태 | 실행 주소와 별도 관리, 비공개 저장소 정보는 공개 데이터에서 제외. 상태는 공개 대상과 독립 |

**숨김은 접근 차단이 아니다.** 초기 JSON에는 숨김 카드를 포함한 전체 데이터가 전달된다. JSON에 들어 있는 값은 누구나 읽을 수 있다고 가정한다. 대상 화면의 URL 역시 비밀 주소가 아니다. 실제 접근 제한이 필요한 정보는 초기 정적 데이터에 넣지 않고, 인증된 서버 저장을 도입한 뒤 다룬다.

검증은 중복 ID, 잘못된 타입, 알 수 없는 필드, 허용되지 않은 링크, 깨진 프리셋 참조를 거부한다. 정해진 필드 안에 비공개 내용을 입력하는 것까지 자동 검증이 판단할 수는 없으므로 공개 전 내용 검토가 필요하다.

## 7. 기술·운영 방향

- 초기: 정적 HTML/CSS/JavaScript + JSON. 신규 DB·로그인 서비스를 필수 의존성으로 추가하지 않는다.
- 유지 관리: 원본 변경 → 데이터 검증 → 화면 확인 → 정적 배포 → 실제 링크 확인. 문제가 생기면 이전 파일·배포로 복구한다.
- 공개 화면은 파일 기반으로 제공해 관리자 서버 도입 여부와 분리할 수 있도록 한다.
- Python 프레임워크나 Supabase 채택은 미정이다. 웹 저장의 필요성, 비용, 휴면 정책, 백업·복구 부담을 비교한 뒤 선택한다.
- 브라우저 UI에서만 관리자 여부를 검사하는 방식으로 서버 변경 권한을 구현하지 않는다.
- 로그인은 허브 관리 권한에만 적용한다. 연결한 프로젝트의 인증과 권한은 각 프로젝트가 책임진다.

## 8. 사용자 흐름

1. 학생: 학생용 주소 열기 → 카드 탐색 또는 검색 → 실행 → 해당 프로젝트로 이동.
2. 교사: 교사용 주소 열기 → 설명·활용 사례 확인 → 실행 또는 자료 공유.
3. 발표자: 미리 선정한 프리셋 주소 열기 → 카드 순서 확인 → 프로젝트별 시연.
4. 관리자: 원본 JSON 또는 편집 도구 열기 → 정보·대상·숨김 수정 → 검증 → 원본 교체 → 배포 → 대상 화면에서 확인.

| 검증 항목 | 통과 기준 |
| --- | --- |
| 대상과 숨김 | 학생·교사 필터와 숨김 조합이 기대한 목록과 일치 |
| 외부 실행 | 실제 등록 링크가 의도한 프로젝트를 열고 새 탭 이동 가능 |
| 미등록 주소 | 클릭 가능한 실행 링크를 만들지 않고 등록 예정 상태 표시 |
| 이미지 | 없거나 로드 실패해도 카드 이름과 실행 기능 유지 |
| 검색·태그 | 현재 대상에 허용된 목록 안에서만 결과 표시, 0건 안내 |
| 발표 | 프리셋 순서 유지, 숨김 제외, 주소로 동일 프리셋 재진입 |
| JSON 편집 | 잘못된 가져오기는 기존 데이터 보존, 편집·내보내기·재가져오기 성공 |
| 저장 안내 | 메모리 적용·다운로드·원본 저장·배포를 사용자에게 구분해서 안내 |
| 데이터 안전 | 위험한 URL·중복 ID·깨진 참조·추가 비공개 필드 거부, 실제 공개 내용 수동 검토 |
| 접근성 | 키보드로 탭·검색·필터·실행 사용, 입력 레이블과 포커스 표시 |
| 화면 크기 | 360px 모바일과 데스크톱에서 주요 콘텐츠 가로 잘림 없이 사용 |
| 오류 | JSON 로드·검증 실패를 화면에 알리고 빈 화면으로 방치하지 않음 |
| 배포 | 공개 URL에서 학생·교사·발표 화면과 정적 자산 로드 확인 |

자동 테스트는 필터·데이터 검증을 확인한다. 실제 외부 링크, 화면 가독성, 모바일·키보드 동작, 배포 상태는 별도로 확인한다.

## 10. 성공 판단

초기에는 분석 서비스를 추가하지 않고 짧은 사용자 확인과 수동 체크로 평가한다. 아래 수치는 측정된 결과가 아닌 초기 목표다.

- 학생이 허브 진입 후 안내받은 자료를 30초 안에 찾아 실행한다.
- 동료 교사가 카드 설명과 사례를 읽고 자료의 목적·활용 방법을 설명할 수 있다.
- 발표자가 별도 링크 모음 없이 준비한 프리셋으로 시연한다.
- 첫 사용에 선정한 실제 실행 링크의 확인 성공률은 100%다.
- 제작자가 공개 설정 변경 후 원본 저장·배포·결과 확인 과정을 재현할 수 있다.

카드 수나 로그인 사용자 수 자체는 초기 핵심 지표로 삼지 않는다.

## 11. 후속 기능 도입 조건

| 관찰된 필요 | 다음 결정 |
| --- | --- |
| 다른 기기에서 자주 수정해야 하거나 파일 교체가 반복적으로 불편함 | 관리자 로그인·웹 저장 검토 |
| 관리자가 두 명 이상으로 늘어남 | 계정별 권한과 변경 이력 검토 |
| 실제로 비공개 자료나 내부 메모를 저장해야 함 | 서버 권한과 공개·비공개 데이터 분리 설계 선행 |
| 동료 교사의 의견을 허브에서 수집해야 함 | 피드백 목적과 개인정보 처리 정책 정의 |
| 자료의 사용 빈도를 알아야 함 | 최소한의 활용 기록과 보관·삭제 규칙 정의 |

후속 기능을 도입해도 기존 프로젝트 코드·DB·로그인을 허브로 합치지 않는다.

## 12. 현재 상태와 다음 작업

현재 카드형 화면, 대상 필터, 검색·태그, 프리셋, 로컬 관리자 편집과 JSON 검증이 구현돼 있다. 실제 미니게임 설명과 대표 이미지를 반영하고 예시 카드를 제거했다. 자동 테스트 4개·빌드·로컬 HTTP 응답·주요 Chrome 화면과 360px 레이아웃 검증은 통과했다. 실제 실행 주소, 외부 배포, 실제 사용자 검증은 남아 있다. 상세 확인 범위와 미검증 항목은 [P0 검증 기록](qa/p0-review.md)에 기록한다.

프리셋 입력 폼과 순서 편집, JSON 붙여넣기·내보내기 내용 확인을 추가했다. 로드 실패 후 복구와 이미지 실패 대체 표시도 검증했다. 파일 업로드·다운로드 검증 제한은 [프리셋 검증 기록](qa/preset-review.md)에 명시한다.

다음 작업 순서는 다음과 같다.

1. 실제 첫 사용 프로젝트 목록과 배포 주소를 확보하고 예시 카드를 정리한다. 주소는 추측해서 등록하지 않는다.
2. 카드 설명·태그·대표 이미지·공개 설정과 활용 사례를 실제 내용으로 채운다.
3. P0 수용 기준을 실제 브라우저와 모바일 크기에서 확인한다.
4. 호스팅 방식을 결정하고 배포·수정·복구 절차를 확정한다.
5. 수업 또는 공유에서 사용해 탐색과 실행 경험을 검증한다.
6. 필요가 확인된 P1 개선과 P2 도입 여부를 결정한다.

초기 호스팅은 GitHub Pages로 선정했다. 미니게임 실행 주소는 확인·등록했으며 Pages 배포와 실제 iPad 검증은 다음 작업이다. 관리자 인증·DB·웹 저장은 현재 도입하지 않는다.
