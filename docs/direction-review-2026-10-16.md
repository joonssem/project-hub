# Project Hub 방향 검토와 사용자 인터뷰

작성일: 2026-10-16 · 상태: 방향 기록, 구현 변경 없음

## 1. 사용자에게 확인한 방향

최우선 과제는 **내가 만든 프로젝트와 최신 실행 주소를 쉽게 관리하는 것**이다.

관리하는 전체 목록을 바탕으로 학생·동료 교사·연수의 층위를 나누고, 제작자가 원하는 프로젝트를 원하는 곳에 원하는 만큼 배치해서 보여준다. 프로젝트는 주로 사용자 GitHub 계정의 여러 저장소에 있으며, 외부 교육 도구도 링크 형식으로 소개할 수 있어야 한다.

현재 구축한 허브는 유지한다. 이번 작업은 논의와 조사 결과의 문서화이며 코드·공개 데이터·데이터 계약·배포 설정을 변경하지 않는다. 기존 PRD의 초기 출시 기준과 운영 검증 항목은 계속 참고하되, 후속 방향과 우선순위에는 이번 사용자 답변을 반영한다.

## 2. 현재 기반과 후속 구상 구분

| 구분 | 현재 기반 | 후속 구상 |
| --- | --- | --- |
| 프로젝트 등록 | 이름·설명·실행 주소·저장소 주소·상태·태그 | 전체 프로젝트 현황과 최신 주소 확인 과정 정리 |
| 대상별 제공 | 학생·교사 화면과 대상별 표시 | 각 대상 안에서도 필요한 일부만 선정한 묶음 |
| 순서 있는 소개 | 발표 프리셋 | 수업·교사 공유·연수별 묶음의 관계 검토 |
| 외부 자료 | 저장소 주소 없이 실행 링크 등록 가능 | 직접 제작·외부 추천 자료를 구분하는 안내 |
| 목록 관리 | JSON 원본과 로컬 편집 도구 | GitHub 후보 수집, 변경 확인, 편집·게시 편의 검토 |

후속 구상은 확정된 구현 명세가 아니다. 새로운 필드나 자동화는 아직 추가하지 않았다.

## 3. 블로그 사례와의 비교

[허니쌤 블로그 원문](https://blog.naver.com/900907his/224443030288)은 여러 저장소와 중복 버전을 정리해 대표 주소 하나에 도구 목록을 제공한 사례다. 글에서는 저장소 67개를 조사하고 수업 활동·학급 운영 도구 27개를 카드로 소개했다고 설명한다. AI와 GitHub를 통한 대화형 수정·배포, 도구별 응답 저장·AI 사용 표시를 소개한다.

공통점은 흩어진 도구의 발견과 관리를 쉽게 한다는 것이다. 블로그는 신규 사이트를 대표 저장소의 하위 폴더에 추가하는 방식을 권장하지만, 이 허브는 각 프로젝트의 저장소·배포·DB·로그인을 독립적으로 유지하고 정보를 연결한다.

자료 전수 정리, 현재 사용 주소 확인, 수업 선택에 필요한 정보 제공은 참고할 만하다. 저장소 통합과 비밀번호 화면은 도입 결정으로 받아들이지 않는다. 블로그 본문을 확인했으며 소개된 도구함의 실제 동작은 별도로 검증하지 않았다.

## 4. 외부 조사에서 찾은 여섯 가지 방향

다음 적용안과 부담 평가는 조사 자료를 바탕으로 한 제안이다. 해당 서비스를 도입하거나 실제 효과를 검증한 결과는 아니다.

| 방향 | 참고 사례와 기능 | 허브에 적용할 가능성 | 고려 사항 |
| --- | --- | --- | --- |
| 제작자용 프로젝트 대장 | Backstage의 소유자·메타데이터 중앙 관리 | 저장소·현재 주소·상태·확인일·다음 작업 파악 | 관리 정보의 갱신 부담. Backstage 자체 도입은 미정 |
| 수업 목적별 자료실 | OER Commons의 주제·교육 수준·자료 유형별 탐색 | 수업 도입·협동 활동·탐구 등 목적별 발견 | 분류와 활용 설명 작성 필요 |
| 수업별 링크 묶음 | Symbaloo의 Webmix 링크·QR 공유 | 이번 수업에 필요한 항목만 선정해 전달 | 묶음의 이름·선정·갱신 관리 필요 |
| 동료 교사용 공개 자료집 | awesome-edtech-tools의 분류 목록과 PR 기여 | 자체 도구·외부 자료·사용법·사례 공유 | 외부 자료의 변경과 중단 관리 필요 |
| 목록 관리 자동화 | GitHub 저장소 API와 링크 점검 Action | 신규 후보·주소 변경·누락·접속 오류 보고 | 자동 수집과 실제 사용 가능성의 차이 |
| 웹 편집·게시 | Decap CMS의 Git 기반 편집·PR 검토 | 원본 파일 교체 단계를 줄이는 편집 흐름 | 인증·권한·게시 설정의 운영 부담 |

## 5. 제안하는 정보와 배치 구조

| 층위 | 핵심 목적 | 정보 예시 |
| --- | --- | --- |
| 제작자 관리 | 전체 현황과 현재 사용 주소 관리 | 저장소, 실행 주소, 상태, 마지막 확인일, 다음 작업 |
| 학생 | 안내받은 활동에 빠르게 참여 | 간단한 설명, 준비 사항, 실행 링크 |
| 동료 교사 | 수업 활용 가능성 판단 | 목적, 대상, 소요 시간, 사용법, 활용 사례 |
| 연수·발표 | 선정한 자료를 소개 순서대로 제시 | 프로젝트 선택, 순서, 소개 맥락 |

권장하는 관계는 **전체 관리 목록 → 공개할 자료 선정 → 대상별·상황별 묶음에 배치**다.

- 한 자료를 한 번 등록하고 여러 묶음에서 참조하면 주소 수정이 여러 배치에 반영되도록 설계할 수 있다.
- 대상별 전체 목록과 개별 수업·교사 공유·연수 묶음을 함께 고려한다.
- 저장소와 프로젝트와 공개 카드가 반드시 1:1일 필요는 없다. 여러 구버전 저장소를 현재 카드 하나에 대응시키거나, 한 저장소의 여러 자료를 별도로 소개할 수 있다. 실제 관계는 인터뷰로 정한다.
- 직접 제작 자료와 외부 추천 자료를 구분하는 안내를 검토한다. 외부 자료에는 저장소 주소가 필수가 아니다.
- 개인 작업 메모·미공개 정보는 공개 데이터와 별도로 관리한다. 현재 JSON의 숨김·대상 필터는 접근 제한이 아니다.

이 구조는 제안이며, 공개 정보와 관리 정보를 저장할 위치나 새 데이터 형식은 아직 결정하지 않았다.

## 6. GitHub 관리와 자동화 검토

### 저장소 기본 정보

설명·실행 주소·README·Topics의 작성 기준을 맞추면 저장소를 찾고 허브 후보로 정리하기 쉽다. 신규 프로젝트에는 공통 안내를 가진 저장소 템플릿을 검토할 수 있다. 템플릿에서 생성한 저장소에 이후 템플릿 수정이 자동 전파되는 것은 아니다.

### 개발 작업과 공개 목록

GitHub Projects는 여러 저장소의 이슈·PR을 표·보드·로드맵으로 모아 관리할 수 있다. 다음 수업 전 수정, 배포 준비, 후기 반영 같은 개발 작업에 활용할 수 있다. 공개 카드와 작업 관리 정보를 각각 어디에서 관리할지는 미정이다.

### 후보 수집과 공개 선정

GitHub API로 저장소 설명·홈페이지 주소·Topics·아카이브 여부·최근 푸시 시점 등을 수집할 수 있다. 권장 흐름은 후보 수집 → 변경 보고 → 현재 주소와 용도 확인 → 공개할 곳 선택이다. 자동 수집한 저장소를 바로 학생 화면에 공개하는 방식은 권장하지 않는다.

최근 푸시 시점만으로 최신 배포본을 판정할 수 없다. 실행 주소의 접속 성공도 게임 참여·응답 저장 등 실제 기능의 정상 동작을 보장하지 않는다. 접속 확인과 실제 사용 확인을 구분한다.

### 유지 보수 종료

오래된 프로젝트는 대체 주소와 사용 안내를 정리한 뒤 아카이브 후보로 관리할 수 있다. GitHub 아카이브는 읽기 전용 전환이며, 이번 작업에서는 저장소를 아카이브하거나 이동하지 않았다.

## 7. 다음 인터뷰에서 결정할 사항

1. 최신 주소의 기준: 학생이 쓰는 안정 버전, 최신 개발 버전, 연수 시연 버전을 각각 관리해야 하는가?
2. 배치 단위: 학생·교사·연수의 기본 목록 외에 수업별·공유 상대별·행사별 묶음이 얼마나 필요한가?
3. 정보의 범위: 공개 카드와 제작자만 볼 관리 대장에 각각 어떤 정보를 둘 것인가?
4. 관리 방식: 대화로 수정, GitHub에서 직접 수정, 브라우저 폼 편집 중 무엇이 가장 편한가?
5. 외부 자료: 직접 써 본 도구만 소개할지, 검토 중인 추천 후보도 관리할지?

아직 이 항목들에 대한 답변이나 구현 승인을 받은 것으로 간주하지 않는다.

## 8. 권장하는 후속 순서

1. GitHub 프로젝트 목록과 외부 도구 후보를 조사해 현재 주소·중복 버전·유지 여부를 정리한다.
2. 소수 자료로 제작자 관리 목록과 수업 목적별 공개 목록을 비교한다.
3. 현재 프리셋을 기반으로 수업·교사 공유·연수 묶음의 필요한 차이를 확인한다.
4. 반복되는 불편을 확인한 후 API 수집·링크 점검·CMS의 도입 우선순위를 정한다.

이번 문서 저장은 위 기능의 착수나 도입을 뜻하지 않는다. 기존 배포·실제 기기 검증의 미완료 사항은 기존 작업 기록을 따른다.
