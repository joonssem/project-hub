# 매주 운영할 때의 불편 예방 조사

조사일: 2026-10-21. 현재 코드와 공식 문서를 바탕으로 한 설계 제안이다. 아래 기능은 구현 완료를 뜻하지 않는다. 서비스 가입·권한 연결·유료 구독·인프라 생성은 수행하지 않았다. 디자인 변경은 후속 작업으로 두고 자료 구조와 운영 흐름을 우선한다.

## 판단

매주 관리자가 해야 할 일은 ‘이번 주 자료를 골라 설명을 확인하고 게시하기’에 한정하는 것이 좋다. 파일 교체, 이미지 주소 찾기, 지난 특집 재입력, 날짜 계산, 반영 여부 추측을 관리자의 주간 작업에서 제거한다.

권장 흐름은 **링크 수집 → 자동 입력 초안 확인 → 특집 복제·선정 → 날짜별 미리보기 → 게시**다. AI는 검색·분류·문구 작성의 초안을 돕고 공개 여부는 관리자가 정한다.

## 저장·게시 방법 비교

### A. GitHub 기반 CMS: 기존 정적 배포 유지

Pages CMS는 GitHub 저장소의 파일·미디어를 편집하며 단일 JSON 파일도 설정 대상으로 삼을 수 있다. GitHub 로그인·App 연결과 `.pages.yml` 설정이 필요하다. 호스팅과 사이트 생성·배포 흐름 자체를 대체하지는 않는다. [공식 소개](https://pagescms.org/docs/), [시작 방법](https://pagescms.org/docs/quick-start/), [파일·형식 설정](https://pagescms.org/docs/configuration/content/).

Decap CMS는 초안 저장을 브랜치·PR로, 게시를 병합으로 연결하는 편집 흐름이 있다. GitHub backend의 인증 설정과 배포 미리보기 연결을 준비해야 한다. [편집 흐름](https://decapcms.org/docs/editorial-workflows/), [GitHub 인증](https://decapcms.org/docs/github-backend/), [미리보기 연결](https://decapcms.org/docs/deploy-preview-links/).

판단: 파일 교체를 빨리 없애려면 유력한 대안이다. 그러나 현재 허브의 보관함·특집 편집 화면과 CMS 편집 화면이 이중화될 수 있다. 공개 저장소의 초안 브랜치를 비공개 자료 저장소로 취급해서도 안 된다. 변경이 Git에 저장된 상태와 실제 사이트 배포 완료를 별도로 표시해야 한다. 도구를 연결했다고 현재 데이터 전체 검증·예약 충돌 검사·정확한 미리보기가 자동 완성되는 것은 아니다.

### B. 현재 관리자 화면에 작은 저장·게시 서버 추가 — 권장 방향

관리자 화면과 학생 화면을 유지하고 관리 데이터 저장, 인증, 공개본 조회를 서버로 분리한다. 후보 구성은 Workers + D1 + 관리자 인증이다. Cloudflare는 정적 파일과 Worker 코드를 함께 배포하는 방식과 Access를 통한 Worker 접근 보호를 제공한다. 이 조합의 허브 적합성은 설계 판단이며 실제 도입 검증은 남아 있다. [정적 파일](https://developers.cloudflare.com/workers/static-assets/), [Access](https://developers.cloudflare.com/workers/configuration/cloudflare-access/).

- 관리자: 허용 계정으로 로그인 → 초안 자동 저장 → 미리보기 → 게시.
- 서버: 관리자 API에서 인증·권한 검증, 내용·참조 검증, 개정 번호 비교, 공개 버전 원자적 생성.
- 학생: 로그인 없이 공개본만 조회. 콘텐츠 변경 때문에 앱 코드를 매주 다시 배포하지 않아도 되는 구조.
- 실패 처리: 초안 저장 실패와 게시 실패를 구분하고, 기존 공개본은 유지한다. 성공 응답만으로 끝내지 않고 공개 API의 버전 확인까지 진행한다.
- 복구: 게시 버전을 보관하고 이전 공개본으로 되돌린다. 데이터베이스 복구와 공개 콘텐츠 버전 복구는 서로 다른 기능이다.

D1에는 시점 복구 기능이 있지만 보존 기간 등은 선택 요금제의 제한을 확인해야 한다. 자체 내보내기도 유지한다. 특정 서비스의 무료 운영을 보장하거나 해당 기능만으로 모든 복구를 해결한다고 가정하지 않는다. [D1 복구](https://developers.cloudflare.com/d1/reference/time-travel/).

장점은 기존 맞춤 관리자 화면에 주간 달력·대량 수집·AI 보조를 자연스럽게 붙일 수 있다는 것이다. 단점은 인증·저장·게시·백업·호스팅을 직접 구현하고 검증해야 한다는 것이다. Workers/D1은 후보이며 지금 계정이나 서비스를 변경할 결정까지 한 것은 아니다. 기존에 운영 중인 신뢰할 수 있는 서버 환경이 있으면 같은 구조를 그 환경에 구현하는 편이 유리할 수 있다.

### C. 당장 적용 가능한 임시 개선

브라우저 로컬 초안 복구, 특집 복제, 날짜 충돌 경고, 게시 전 검사는 서버 도입 전에 구현할 수 있다. 단, 로컬 저장은 다른 기기 동기화·진짜 웹 저장·백업을 대체하지 못한다. 브라우저 데이터는 삭제·축출될 수 있으며 비공개 모드 등에서도 동작이 달라진다. [브라우저 저장 특성](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

판단: C는 유실과 반복 입력을 줄이는 임시 단계다. A와 B를 모두 완제품으로 구축하기보다 B를 목표로 정하고, 인프라 준비가 길어질 때 A를 별도의 대안으로 검증하는 것이 중복 개발을 줄인다.

## 주간 예약을 더 단순하게 만드는 방법

‘독도 교육 주간’, ‘안전 교육’, ‘협동 활동’을 몇 주 앞서 준비하고 공개 가능한 일정으로 게시한다. 학생 화면은 한국 날짜에 맞는 특집을 선택한다. 미리 공개해도 되는 링크·소개에 한정하면 월요일 아침에 누군가 버튼을 누르거나 새 배포를 실행하지 않아도 된다.

GitHub Actions의 예약 실행은 지연되거나 일부 작업이 누락될 수 있고, 공개 저장소가 60일 동안 비활성이면 예약 작업이 비활성화될 수 있다. 그러므로 수업 시작 시각의 주제 전환을 Actions 예약 배포 하나에 의존하지 않는 것이 좋다. 링크 상태 점검처럼 약간 지연되어도 되는 보조 작업에는 사용할 수 있다. [GitHub 공식 예약 실행 제약](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

예약 자료를 시작일까지 비공개로 보관해야 한다면, 미래 자료를 학생 JSON에 미리 포함하지 않는다. 서버가 신뢰하는 한국 날짜로 현재 공개할 항목만 응답해야 한다. 지금의 브라우저 날짜 선택 방식은 표시 예약이며 접근 제한이 아니다.

학생 화면은 현재 주제와 자주 쓰는 기본 자료를 함께 유지하고, 특집은 필요할 때만 나타나게 한다. 모든 자료에 주간 종료일을 붙이면 관리가 불필요하게 번거로워진다.

## 수집과 AI를 함께 쓰는 방법

1. URL을 붙여넣으면 제목·설명·썸네일 후보를 수집한다. Open Graph는 제목·이미지·설명 등을 제공할 수 있지만 모든 사이트에 완전한 정보가 있다는 보장은 없다. 수집 실패 시 직접 입력으로 진행한다. [Open Graph 원문](https://ogp.me/).
2. URL의 fragment·쿼리를 무조건 삭제하지 않는다. 웹앱의 활동 경로·방 입장·자료 식별에 쓰일 수 있다. 정규화한 주소와 실제 저장 주소를 구분하고 유사 링크는 합치기 후보로만 표시한다.
3. GPT 등 모델은 근거를 확인한 페이지 내용으로 학생용 한두 문장 소개, 태그 후보, 검색 동의어를 작성한다. 직접 확인하지 못한 본문은 추측해 채우지 않는다.
4. 원문 링크와 제작자·제공처를 유지한다. 추천 학년·소요 시간·로그인 필요 여부가 추정이면 관리자 확인 대상으로 표시한다. ‘검증됨’ 표시를 모델 추정으로 만들지 않는다.
5. 관리자가 ‘다음 주 독도 관련 자료 골라줘’라고 요청하면 보관함의 기존 자료와 새 후보를 구분해 제안한다. 자동으로 학생에게 게시하지 않는다. 외부 API 사용·비용·전송 범위는 구현 시 선택하며 이번 조사로 AI API를 연결한 것은 아니다.

외부 URL을 서버에서 수집할 때는 인증된 관리자 요청만 허용하고 내부망·로컬 주소, 리다이렉트, 응답 크기·시간 제한을 처리해야 한다. 단순한 HTTP(S) 문자열 검사만으로 서버 수집을 안전하게 만들 수는 없다. [OWASP 서버 URL 수집 지침](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).

## 링크·이미지 점검

lychee처럼 기존 링크 검사기를 활용할 수 있다. 허브에서는 JSON의 실행 주소·이미지 주소를 뽑아 검사 입력으로 전달하는 연결 작업이 필요하다. [공식 저장소](https://github.com/lycheeverse/lychee).

검사 결과는 ‘HTTP 응답 확인’과 ‘수업에서 실제 사용 확인’을 구분한다. HTTP 200이어도 로그인·차단·서비스 종료 안내일 수 있고, 403이어도 자동 검사만 차단한 것일 수 있다. 링크 검사 오류 하나로 자료를 지우지 않는다. 주간 특집에서 쓸 자료만 우선 점검하고 대체 자료를 고를 수 있게 한다.

이미지는 원격 주소 입력, 직접 업로드, 기본 대체 썸네일을 제공하는 구성이 좋다. 원격 이미지의 존재나 수집 성공을 재게시 허가로 취급하지 않는다. 외부 제작자의 이미지 업로드·저장은 허용 여부를 확인한 경우에 사용한다.

## 실제로 완료했다고 판단할 조건

- 관리자 노트북에서 저장한 초안을 다른 기기에서 이어 편집할 수 있다.
- 저장하지 못한 상태와 서버에 저장된 상태를 구분한다. 편집 중 새로고침 후 복원된다.
- 자료를 여러 개 수집해도 게시 전에는 학생 응답이 바뀌지 않는다.
- 지난 특집을 복제해 날짜와 자료만 바꾸면 다음 주 구성이 준비된다.
- 날짜 중복·자료 0개·표시 제외 이유를 게시 전에 알 수 있다.
- 게시 실패 중에도 기존 학생 화면이 유지된다. 성공 후 공개 버전을 확인할 수 있다.
- 이전 버전 복구가 가능하며 두 기기의 동시 저장이 조용히 덮어써지지 않는다.
- 서버 조회만으로 미공개 보관함을 읽거나 비관리자가 변경할 수 없다.
- 특집 종료 후 기본 화면, 한국 날짜 경계, 실제 iPad·학교망 동작을 확인한다.

기능 도입 순서는 **저장·게시·복구 → 복제·일정 검토 → 빠른 수집·중복 확인 → 링크 점검 → AI 문구·선정 보조**를 권장한다. 이는 구현 순서에 관한 판단이며 디자인 개편과 독립적으로 진행할 수 있다.
